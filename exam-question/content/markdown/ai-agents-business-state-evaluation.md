# 不同执行路径如何验收

ID: business-state-evaluation
Library: ai-agents

## 题干

两个 Agent 使用不同工具路径完成同一业务目标，怎样制定公平且可重复的验收？

## 参考答案

1. 目标状态：把成功定义为可检查的业务最终状态；以状态或产物断言而非固定调用顺序验收。

2. 过程约束：允许满足目标的合理替代路径；仍检查权限与副作用等必须遵守的约束。

3. 可重复性：固定初始数据及环境条件；记录执行证据并在相同条件下复测。

最近我给一个商品上架 Agent 做了最小 Eval 闭环。

用户提供商品图片、价格和库存，
本地 Runner 调用 Agent Chat。

任务结束后，我没有先让 LLM Judge 判断
“它看起来有没有完成”，
而是直接读取最终商品数据：

商品名称和图片是否存在，
价格和库存是否与用户输入一致，
必要字段是否已经完成。

再从 Trace 里检查必要行为、禁止行为，
以及影响任务完成的未恢复错误。

这个实践让我确认了一件事：

Agent 已经是一个会波动的被测对象，
Eval 就不要再无必要地增加一次概率判断。

能查最终状态，
就不要让模型判断“看起来像完成”；
能直接比较字段，
就不要让模型判断“大概正确”。

确定性规则不是为了消除 Agent 的不确定性，
而是为了避免把 Judge 的不确定性混进来。

当然，这不等于固定 Agent 的完整执行路径。

这套 Eval 只检查最终结果是否正确，
必要行为是否出现，禁止行为是否发生。
只要没有越过业务边界，
Agent 可以通过不同的合法路径完成任务。

LLM Judge 仍然有价值，
但更适合相关性、表达质量等开放语义。

事实比较交给代码，
开放语义交给范围明确的 Judge，
业务标准不清楚时先由人确认。

另一个现实问题是成本。

10 个黄金 Case，比较 2 个版本，
每个 Case 重复 3 次，
就是 60 次有效运行。

所以，并不是每个修复
都要留下一个完整的 Agent Case。

更值得思考的的是：
哪一层能用最低成本保留这次失败机制？

能用单元测试、Contract Test 或 Guardrail 保护的，
就不必全部留到 Agent Eval。
