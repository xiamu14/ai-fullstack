# 必须每次执行的检查，为什么不应只写在 Prompt 中？

ID: hook-prompt
Library: ai-agents
Version: 2026-10-24.1

## 题干

必须每次执行的检查，为什么不应只写在 Prompt 中？

## 参考答案

概率性模型遵循指令不能替代确定性检查。

职责划分：Prompt 引导方案与风格；必须执行的控制放程序生命周期；不能声称 Hook 使整个 Agent 确定。

执行时机：工具调用前检查权限和保护路径；调用后运行校验并记录状态；完成前核验质量门。

独立验证：Hook 失败须阻止受控动作；CI 保留独立验证；有判断归属的问题交人工审核。

## 来源

[Agent Hooks：给 agent 工作流加上确定控制](https://www.xiaohongshu.com/explore/6a07b31a000000003700ed28)，奥森木，2026-05-16T07:58:18+08:00，仅正文。

什么时候用 hook。有个简单判断法：要求里出现 always / never / block / record / run / verify 这类词，就该放 hook 不是 prompt。"不要编辑生成的文件"、"完成前跑测试"、"测试挂了不许说做完"——这些都是 hook 该管的，模型有时候记得有时候忘。代码风格、命名约定这类灵活引导留 prompt 就够。

6 个生命周期点够覆盖起步。按 agent 工作流时间线：
- SessionStart 加载项目约定 / 活动约束
- UserPromptSubmit 按主题给 prompt 加上下文 / 拦坏 prompt
- PreToolUse 工具调用前拦截 / 批准 / 修改
- PostToolUse 工具调用后跑测试 / 记日志 / 写状态
- Stop 检查质量门，没过就阻止"假完成"
- SessionEnd 写最终审计 / 清临时状态

操作模型很干净：event → matcher → handler → outcome。匹配的事件触发时你的 handler 一定会跑，结果可以是上下文、决策、副作用或记录。handler 可以是 shell 命令、HTTP 请求、MCP 工具调用、子 agent，最便携的是 shell 调 Python 脚本。

关键边界：hook 不让整个 agent 跑成确定性的。模型仍然自由决定方案、编辑、工具调用、恢复路径。hook 让确定的是窄但有用的那一块——一些必须每次都跑的检查和副作用。

4 层职责要分清楚：项目指令（prompt）管风格架构 → hooks 管必跑控制 → CI 管独立验证 → 人审管判断归属。把所有东西塞 hook 会过度自动化，全塞 prompt 会依赖模型听话。

采用路径就 3 步，别一上来想搭完整治理系统：
1. 拦保护路径 · PreToolUse 拦编辑 generated/、.env、敏感 fixture
2. 加质量门 · PostToolUse 跑最快有用的测试，结果写状态文件
3. 加完成门 · Stop 读上一步状态，挂了就阻止 finish

跑顺这 3 步再加 SessionStart 上下文、UserPromptSubmit 路由、SessionEnd 审计——锦上添花。

最有用的一句收束：hook 把可重复的规则，从"模型记忆"搬进"生命周期上有命名的代码点"。 模型还能自由推理写代码，但测试、政策、日志、完成门——作为确定性的部分——在工作流里运行。
