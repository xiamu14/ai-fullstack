# 任务状态为何需要独立验收

ID: verified-task-state
Library: ai-agents
Version: 2026-10-24.1

模块：决策编排 · 难度：L3

## 题干

长任务如何避免 Worker 自称 Done 后错误地把下游任务全部解锁？

## 参考答案

1. 状态定义：为子任务定义明确的完成条件；用结构化任务状态记录已验证的进度。

2. 独立验收：由独立验证者检查文件测试或业务环境的真实结果；验证者不应通过擅自修复产物来掩盖执行者未完成。

3. 状态推进：仅在证据满足条件后将任务标为完成并推进依赖；验收失败时保留原因并重新规划而非盲目继续。

阿里 DreamX Team 的一篇新论文 LongHorizon-Harness，讨论了一个很现实的问题：为什么 Agent 明明越来越聪明，但任务一长，还是很容易跑偏？

很多人会把问题归结为 Context 不够长。但这篇论文给出了另一个答案：长程 Agent 真正缺的可能不是更大的 Context，而是更可靠的 Task State。

传统 Agent 会不断保留执行轨迹：做过什么、调用过什么工具、得到过什么结果，然后让模型从越来越长的历史中判断“我现在做到哪了”。

结果就是任务越长，Context 越混乱，甚至连哪些事情真的完成了都搞不清楚。

LongHorizon-Harness 换了一个思路：与其记住所有过程，不如只记住经过验证的状态。

为此，它设计了 Manager、Executor 和 Auditor 三个角色。
Manager 管理任务状态，把大任务拆成有明确验收标准的小任务；Executor 负责真正干活，而且每轮都可以使用 Fresh Context，不需要背着几十步历史继续工作；最关键的是 Auditor，它不相信 Executor 自己说的“Done”，而是独立检查环境，确认文件是不是真的生成了、测试是不是真的通过了、任务是不是真的完成了。
而且 Auditor 原则上是 Read-Only：执行的人不能同时负责给自己验收。
效果也很明显，使用 Qwen 3.7-Plus + Claude Code，在通用的Benchmark 仅仅改变 Harness 都能获得提升。

Agent Capability 不只是 Model Property，也越来越是一种 System Property。
模型决定某一步能不能想明白，而 Harness 决定几十、几百步之后，这件事情到底能不能真正做完。
对于企业 Agent，过去 Eval 更多发生在上线之前，未来它可能直接进入 Agent Runtime：Execute → Evaluate → Update State → Re-plan。

模型决定 Agent 有多聪明，Harness 决定这个聪明的家伙，能不能把事情真正做完。
