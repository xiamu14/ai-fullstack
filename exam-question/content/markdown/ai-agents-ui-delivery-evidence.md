# 网页生成后如何验收

## 题干

Agent 已生成网页代码且构建成功，为什么仍不能直接认定页面可以交付？应该收集哪些证据？

## 参考答案

1. 实际运行：页面需要在目标运行环境中实际打开；检查控制台与图片等资源是否正常加载。

2. 用户行为：验证关键按钮或表单等用户路径确实可用；检查遮挡布局与窄屏等实际显示问题。

3. 证据范围：保留运行截图日志或交互结果供核对；区分功能技术检查与内容审美等仍需人工判断的事项。

这次看的是 `webapp-testing`，一个专门帮我做网页验收的 Skill。

它解决的问题很具体：AI 写完页面以后，不要只停在“代码生成了”，而是让真实浏览器打开页面，看画面到底能不能交付。

我最喜欢它的一点，是它把网页交付变得更像一套证据链：
打开页面，截图，看 console，确认图片有没有加载，再把结果整理出来。
这听起来很小，但我以前很多页面问题，都是在这一步才发现的。
比如：
图片路径没坏，但页面看起来还是空；
桌面端没问题，手机端一缩就挤在一起；
按钮还在，但被其它元素盖住了；
console 没报红，不代表用户看到的画面就舒服。
我这次用它跑了一组本地 HTML 周报，结果是：7 个页面都能打开，关键元素都在，broken image 和 console error 都是 0。

所以我会把它放进以后做页面的最后一步：代码完成之后，再让浏览器替我看一遍真实画面。
它不负责替我审美，也不负责判断内容好不好。
它更像一个交付前的“冷静检查员”：把我容易漏掉的页面问题先拦下来。

如果你也经常用 AI 做页面、报告页、活动页或小工具，我觉得这个 Skill 值得收藏。
