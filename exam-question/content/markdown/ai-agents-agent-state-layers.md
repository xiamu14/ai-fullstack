# 对话状态与执行状态如何区分

## 题干

请区分 Agent 的对话状态、执行状态、长期记忆和外部业务状态，并说明各自怎么使用。

## 参考答案

1. 会话与执行：对话状态保存当前交互所需的消息；执行状态显式记录任务阶段进度及工具结果。

2. 记忆与业务：长期记忆保存跨会话可复用信息；外部业务状态以数据库或文件等真实环境为准。

3. 存取策略：根据生命周期和恢复要求选择存储方式；构造当前上下文时按需投影状态而非把所有历史塞入窗口。

你发现没有——有的 AI Agent 能记住你说过什么、工具调到哪里、任务完成到哪一步；有的却像「金鱼记忆」，每问一句就失忆一次。

这背后的区别不是模型好坏，而是一个根本性的架构设计：有状态 vs 无状态。      Agent 的「状态」（State）是指在多次 LLM 调用、工具执行和用户交互之间持续保留的上下文信息。它分为四个层次：

🧠 对话状态——最浅层，就是 LLM 的 messages 数组。每一次推理请求都需要携带历史对话、System Prompt 和工具定义。生命周期短，对话结束即释放。

🛠️ 执行状态——中层，Agent 循环中的子任务进度、工具返回值和变量绑定。比如「正在搜索 → 找到 3 条 → 正在分析 → 已生成报告」这个过程，每一步的状态都不能丢。

📚 记忆状态——长生命周期，跨会话持久化。用户隔天回来说「上次那个分析报告呢？」——Agent 需要从记忆库中精确召回。

🗄️ 外部状态——最持久，数据库、文件系统、环境变量，是 Agent 操作的真实世界。

状态管理的四大核心挑战：上下文窗口有限（对话越长越「失忆」）、并发一致性问题（并行工具调用写同一状态产生竞态）、故障恢复（第 8 步崩溃了要从头跑吗？）、跨会话协调（用户能继续上次的话题吗？）。

最佳实践中，生产级 Agent 采用三层存储架构（内存→持久化DB→向量库），用 Checkpoint 实现断点续跑，用 Event Sourcing 记录每一次状态变迁——这已经不是「优化选项」，而是 Agent 能否真正上线的分水岭。

通过分层记忆和结构化上下文管理。短期记忆保存当前任务关键信息，中期记忆用滑动窗口保留最近交互，长期记忆用向量检索跨会话。同时采用状态机追踪任务进展，用结构化 prompt 明确当前阶段、已做动作和待办事项。
核心原理
Agent 的多轮管理实质是 信息压缩与检索。每次决策时，prompt 包含：
· 系统提示 + 任务目标（静态）
· 当前任务步骤状态（状态变量，由解释器维护）
· 最近 N 条对话（滑动窗口）
· 检索到的长期记忆片段（如用户偏好）
