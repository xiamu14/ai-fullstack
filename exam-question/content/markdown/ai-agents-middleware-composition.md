# 多层中间件如何组合

ID: middleware-composition
Library: ai-agents
Version: 2026-10-24.1

模块：工具执行 · 难度：L3

## 题干

给工具调用叠加日志、鉴权和计时中间件时，为什么必须明确顺序与错误传播？

## 参考答案

1. 调用形状：中间件接收原 handler 并返回可调用的增强 handler；保留调用需要的输入输出与异步语义。

2. 嵌套顺序：明确请求进入时各层执行的顺序；响应或异常沿包装层返回时按嵌套关系处理。

3. 控制边界：区分只能观察的回调与能够阻断或改写的包装器；测试拒绝异常和重复调用等边界避免漏执行或多执行。

我实习时参与过一个产品研发。当时项目几乎没有文档，我问实习 mentor：这个系统到底应该怎么看？他说：
代码就是文档。
那时候我不是很理解这句话。多年以后，我慢慢理解了它的含义：这句话是对的。
代码之所以能成为文档，是因为读代码的人手里有一套密码本。同一行代码，一个人看到语法，另一个人看到模式，再往深一点，有人能从代码形状里读出背后的抽象。
这套密码本不一定来自团队内部，也可以来自更通用的理论：范畴论、FP、类型系统、effect（效应）、composition（组合）。两个学过范畴论和 FP的人，哪怕不在同一个团队，看到 map、flatMap、A => F[B]、handler => enhancedHandler，也能读出组合、上下文、效应、边界和解释器。
Agent framework也是一样。只看 API，LangChain、Claude Code、workflow框架里的 hook、middleware、handler、callback、interceptor都像“某个时机插一段代码”。但如果没有更稳定的抽象，就很难判断：它只是观察，还是能改写？能不能阻断？有没有拿到 handler？包完以后原调用形状还在不在？多个 middleware叠起来，顺序怎么解释？
这就是这篇文章要看的东西：不是某个框架怎么用，而是这些 API背后可以迁移的结构。
(A => F[B]) => (A => F[B])
