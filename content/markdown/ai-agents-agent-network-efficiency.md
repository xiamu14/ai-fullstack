# Agent 通信网络如何衡量

## 题干

多个 Agent 通过网络交换信息和任务时，应怎样设计消息契约并评价网络是否有效？

## 参考答案

1. 消息契约：明确消息对应的发送者任务与期望交付；区分信息广播与需要回复的定向任务。

2. 资源效率：统计通信消耗的 Token 延迟与重复消息；把通信开销与完成任务的实际收益关联。

3. 运行边界：明确身份权限和消息处理范围；验证超时重复或失败消息不会无限传播。

我在公司内部搭了一个小型的 Agent 局域网，把几位同事的 Agent 连接了起来。太有意思了。

说实话，之前我一直没想明白 Agent to Agent 的使用场景，觉得这个概念挺抽象的，这一次算是彻底具象化了。

我们同事有的用 Codex，有的用 OpenClaw，有的用 Hermes。无论用的是什么 Agent，这两天我们都让它正式接入到了 EigenFlux。

简单来说，EigenFlux 是一个让 Agent 互相连接和通信的网络。接入之后，不同的 Agent，可以像加好友一样建立联系，互相发送消息、交换信息和传递任务。

做个类比的话，它就是给 Agent 准备的互联网。毕竟现在我们用 Agent 还是单机模式。

但 Agent 能做的事情越来越多，如果 Agent 和 Agent 之间也能协作，那这事就有意思太多了。

EigenFlux 目前主要有两种 Agent 之间的连接方式：

第一种是广播。Agent 把需求或信息发到网络里，其他 Agent 看到后可以响应。

当然陌生 Agent 之间的广播会先经过平台节点审核。

第二种是好友和私信。两个 Agent 加为好友后，可以持续私聊，更高频地交换信息和协作。加好友需要经过人类确认。

我和同事之间就是通过第二种方式接入的。大家先让各自的 Agent 加为好友，再把日常工作中的信息和任务直接发给对方的 Agent。

说一下我的具体场景。

这半个月我在做一个产品，做完之后内测，会收集用户和同事的反馈。

之前的流程是，有什么问题，大家扔到群里，我一一处理。

现在新的流程我们尝试调整为了：同事发现了问题，直接通过自己的 Agent，把反馈发给我的 Agent 就行了。

我的 Agent 收到之后，会按照要求把这条反馈整理成一个可理解的格式。

如果信息不够清楚，它会再跟对方的 Agent 交互，获取进一步的信息，把这条 Bug 的描述补充完整。
