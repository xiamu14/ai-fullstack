## 题干

请区分提示词前缀缓存与语义答案缓存，并说明语义缓存需要哪些边界。

## 参考答案

1. 缓存区别：前缀缓存复用模型对相同前缀的计算但仍需模型推理；语义答案缓存复用已有回答可以绕过本次生成。

2. 命中约束：命中需要检查相似度及问题适用条件；隔离用户或租户以避免跨权限复用。

3. 失效监控：根据知识更新或时效设置失效策略；监控误命中对回答质量的影响。

Redis 打造了一款缓存方案，可将 LLM 成本削减 90%！
生产环境中的 LLM 应用并不会每次都收到全新的问题。
以客服助手为例，它可能先后收到以下三种提问：
“购买月度套餐后还能退款吗？”
“月度订阅支持退款吗？”
“我能取消套餐并拿回钱吗？”
措辞各异，但底层问题和答案完全相同。
然而 LLM 应用会把每个版本都当作新请求处理：组装 Prompt、发送给模型、生成一个或许早已生成过的答案。

前缀缓存（Prefix Caching） 能减少部分重复调用。当多个请求共享相同的系统提示词或上下文前缀时，模型可以复用已计算好的 KV 状态。但请求依然会抵达 LLM——新 Token 仍需处理，完整答案仍需解码。换言之，即便命中前缀缓存，仍免不了再一次生成调用。

要彻底解决这个问题，不能只在模型内部缓存计算结果，而应在模型外部缓存已生成的响应。
当新问题到达时，系统先将其向量化，与历史已回答的问题进行相似度比对。若找到足够接近的匹配项，直接返回存储的响应，不再调用 LLM。
一次缓存命中，意味着省掉了另一次 LLM 调用所涉及的全部输入 Token、输出 Token 和解码时间。
在实际落地中，关键难点在于判断哪些问题可以安全地共享答案。生产级部署需要精心调优相似度阈值、过期策略、数据隔离机制，以及对错误匹配的监控告警。
如果你想在生产环境中使用这套方案，Redis LangCache 它在底层自动生成向量嵌入、检索历史响应，在下一次模型调用发生之前就返回匹配答案。同时通过 Redis Cloud 提供访问作用域控制、自定义过滤、TTL 与驱逐策略、以及缓存命中率监控等全套运维能力。

Redis 官方数据显示，API 成本最高可节省 90%，缓存命中响应速度最高可达 15 倍。实际收益取决于你的业务负载中有多少“可安全复用”的重复提问。
