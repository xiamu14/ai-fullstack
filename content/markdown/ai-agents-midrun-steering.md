# 长任务如何接受中途补充

## 题干

Agent 正在执行长任务，用户补充了更高优先级约束，系统应该怎样接入这条消息？

## 参考答案

1. 消息接入：将用户补充与原任务关联并放入受控消息队列；区分普通补充与取消等高优先级控制信号。

2. 安全交接：在可中断点或步骤边界读取新消息；对不可中断或已有副作用的动作先核对实际状态。

3. 计划更新：把有效补充写入当前执行上下文并调整后续计划；避免继续执行已被新约束否定的待执行动作。

如果你用过 LangChain 、Devin、OpenAI Assistants，会发现它们有个共同的工作方式：你说一段，它跑一段，中间你插不进话。想加补充？要么整个对话停掉再resume对话，破坏对话“连续性”，要么干等。
这不是产品做得差，是它们都建立在同一个默认假设上：Agent 的工作单位是"turn"，一个不可分割的“输入→生成→输出”原子。

一个真正像人的Agent，真的会是这样交互吗？两个顶尖团队在完全不同的层级和方式，来回答这个问题。

🧠 Thinking Machines 在模型层：发了 TML-Interaction-Small，200ms 块对齐，同时听同时说。
Mira 在博客里直接说："行业卷 autonomous agent，不是用户需要的，是架构只能做到这里。"

🛠️ Claude Code 在Harness层：async generator + 三级优先级队列。模型还是 turn-based，但 harness 假装它不是——你"任务中插话"时，系统不开新对话，而是把消息塞回 agent 的工具结果里。

它们解决的场景不重合(实时语音 vs coding 长任务)，但反的是同一个共识:

turn 不该是不可分割的原子。
