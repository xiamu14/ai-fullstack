# MCP 工具应按底层 API 划分，还是按用户意图设计？

## 题干

MCP 工具应按底层 API 划分，还是按用户意图设计？

## 参考答案

围绕模型要完成的任务暴露清晰工具。

任务建模：先明确用户目标；确定完成任务必需的输入；返回能直接支持下一步的结果。

接口设计：工具名称说明意图；描述精炼且不重复名称；参数尽量简单扁平并明确约束。

验证边界：用真实任务验证选工具准确性；保留权限与参数校验；高风险副作用不因合并工具而绕过审批。

想和大家真诚分享下我们最近在 MCP 上踩的坑。

过去几个月，很多人都在说 MCP 已死，觉得 Skills + CLI 更好用。说实话，Skills + CLI 确实很棒，但我自己的体会是，当你需要让 AI 助手直接向用户展示产品功能时，MCP 依然是最顺手的工具。

不过 MCP 有个被骂得最狠的问题——上下文太臃肿。我们团队试过，加载 7 个 MCP 工具，光工具描述就吃掉 6.7 万 token。你看这个数据：

说实话，这个锅不能全甩给 MCP 协议。问题出在我们怎么设计工具本身。只要设计得当，完全可以把 token 开销压到很低，同时让模型更稳定、更听话。

第一条法则：MCP 是界面，不是 API。 很多人一上来就把 MCP 当 API 设计，给模型塞一堆底层接口。其实模型不关心你背后调了什么服务，它只想知道：我要用什么工具来完成用户的指令。所以我们的设计思路应该反过来，先想清楚用户要什么，再决定暴露什么工具。

那具体怎么设计呢？我从用户的角度出发，问自己几个问题：

- 用户想达到什么目的？
- 他们会怎么提出这个需求？
- 我需要他们提供哪些信息？

我应该返回什么，才能让模型直接给出答案？

这些问题的答案，就是你的工具结构。用户意图就是工具名，提问方式就是提示示例，必要信息就是输入参数，返回内容就是输出结果。
想清楚这些，再去考虑实现细节：调哪个服务、做什么校验、怎么转换数据。

如果你是第一次写 MCP 服务器，我建议你先把范围缩到最小，从只读功能开始。快速搭一个原型，拿 LLM 去测，跑通一遍你就会发现哪里需要调整。迭代几轮，架构就自然清晰了。

第二条法则：控制工具数量，别贪多。

有了第一条的指导思想，你自然会把多个相近功能合并成一个。比如，不要分别搞“查客户”、“开发票”、“下PDF”三个工具，直接给一个 ，名字越长越清晰，模型一看就知道干嘛，选错的概率大大降低。

输入参数也一样，尽量扁平，别搞深层嵌套。每多一层，模型就多一分晕头转向的风险。

第三条：描述要精炼，错误要带路。

描述不是说明书，别啰嗦。工具名已经说了“生成发票”，描述就不要再重复“此工具用于生成发票”。用祈使句，直接告诉模型怎么做。比如：“为当前用户生成指定日期的发票，日期未填则默认今天。

第四条：输出做减法，别什么都往回复里塞。站在模型的角度裁剪输出，只给它下一轮对话最需要的那些字段
