# 失败轨迹如何定位根因

ID: failure-dependency-diagnosis
Library: ai-agents
Version: 2026-10-24.1

模块：工程质量 · 难度：L3

## 题干

Agent 运行一百步后失败，为什么不能简单把最早的报错当作根因？应怎样定位决定性错误？

## 参考答案

1. 依赖建模：把动作结果与所用上下文关联成依赖结构；核对判断与实际动作是否符合当前任务约束。

2. 信息区分：区分从未获得必要信息与已经获得却未使用；依据原始事件而非仅凭最终解释来判断。

3. 决定性错误：检查早期错误是否已恢复以及错误如何传播；定位真正导致目标无法完成的关键错误并验证因果链。

## 来源

[微软x清华 AgentScope：别只把日志给大模型](https://www.xiaohongshu.com/explore/6aa17547000000002b001731)，AI拯救打工人（幻觉版），2026-09-09T23:48:00.000Z，仅正文。

Agent 跑了 100 步，最后失败了。问题是：到底哪一步出了错？
这件事，可能比让 Agent 把任务做对更难。

微软、清华等最近的论文，提出一个 Agent 故障诊断框架 AgentScope。
它解决的不是“Agent 成功还是失败”，而是两个更工程化的问题：错在哪一步？为什么错？

很多 Agent 平台现在已经有 Trace： 调用了什么 Tool、Tool 返回什么、模型说了什么，都能看到。但有 Trace，不代表能 Debug。
传统做法是直接把整段执行日志丢给另一个大模型：“帮我看看哪里错了。”

论文实验里，这种 Vanilla LLM Judge 在故障类型识别上的准确率只有 18.15%。
AgentScope 换了一种思路。

第一步，它把 Agent 的执行轨迹转成一个 Reasoning-Action Graph。
不只是保存日志，而是明确：意图是什么、用了哪些上下文、做了什么判断、调用什么工具、获得什么结果，以及步骤之间的数据依赖。

第二步，也是这篇论文最有意思的地方：Neural Invariant，神经不变量。
传统程序可以写：“未审批，不允许付款。”
Agent 的很多规则却是语义性的，比如：“Agent 实际执行的动作，是否符合它刚刚说的计划？”
这种规则很难用普通代码判断，于是论文让 LLM 只负责判断这个局部问题。

也就是说，大模型变成“检查某条明确规则是否成立的函数”。

论文还区分了一个很有价值的概念：Insufficient Context 和 Context Miss。
前者是真的没有信息，后者是信息明明已经给 Agent 了，它却没用。

还有一个我非常喜欢的设计：Decisive Error。
Agent 最早犯的错，不一定是真正导致任务失败的错。
比如第一次搜索失败了，但 Agent 后面恢复了；真正让任务失败的，可能是后面陷入循环、提前终止，或者用了错误的工具。

Agent Evaluation 正在从“判断最终答案对不对”，走向“诊断整个执行过程为什么失败”。
Agent 时代真正缺的，可能不是更多日志，而是一套 Debugger。
