# 如何委派可验收的任务

ID: verifiable-delegation

## 题干

把开发工作交给 Agent 时，怎样避免只收到“已完成”却无法判断实际效果？

## 参考答案

1. 目标表达：将要求写成用户可观察的结果与约束；明确交付物及其适用场景而非只给模糊角色。

2. 验证依据：为关键结果指定可运行检查或原始证据；主动寻找反例以避免仅收集支持性输出。

3. 人工责任：由负责人理解关键取舍并审查高风险决定；依据验证证据验收而非只信 Agent 自评。

先说结论：他说我们不是用不好 AI，是给的目标太客气了。
Felix Rieseberg 是 Claude Code 桌面版的负责人。他近期写了篇教程，意思翻过来就是——用 AI，应该更有野心一点。

他把"野心"分了四层：
1、速度：更快做完同样的事（已经很成熟，不必教）
2、高度：提高任务的抽象层次，别派任务，直接要结果
3、深度：像顶尖专家那样做，用他们的工具和原始材料
4、广度：把其他领域的做法拉进来
真正有用的是他给的具体动作。

一、故意定一个"不合理"的目标。
假设网站加载 10 秒，你想压到 5 秒。他建议：直接把目标定到 0.2 秒。
模型说做不到？那就继续告诉它：这个问题完全可以解决，再试。
二、把名词换成动词。
"做一份季度汇报 PPT"——这是名词，是一个交付物。
换成："在 30 分钟内，让一群忙碌的人信服你对事情前因后果的解释，并在情况还不明朗时作出决策。"
名词会把做法框死，动词会暴露你真正的目标。
三、别只让它"像专家一样思考"。
你让它"像专业人士"，它往往只是换一套专业词汇，方法一点没变。
要追问的是：真正的专家会看哪些原始资料？会用哪些工具和方法？然后把这些写进任务里。
他举的例子很具体：别让它拿 Markdown 表格糊弄，要数据库和统计模型。
四、别让 AI 给自己打分。
写代码就实际跑起来；做预测就换一份新数据去验；做判断就回原始材料找反例。
既要找支持证据，也要找能推翻它的证据——自己评自己，永远是好话。

还有一个特别好用的判断信号：
如果这件事做完之后还要开会讨论，说明你要的其实不是那个交付物，目标该再往上提一层。
他自己的例子：从"帮我修这个崩溃"改成"让我们的应用保持不崩溃"。
我看完真正被戳到的是那句"我们太保守了"。
平时我派活都是"帮我写个 X""把这段改顺"——全在动作层面，目标还定得很客气。0.2 秒那个例子提醒我：不是我要求太高，是我根本没提要求，只是在描述动作。
你上近一次给 AI 定的目标，是不是也太客气了？
