# 滚动摘要为什么不能替代全部历史原文？

## 题干

滚动摘要为什么不能替代全部历史原文？

## 参考答案

摘要压缩会损失细节，关键事实需另行保存并可回溯。

损失识别：摘要是有损压缩；递归摘要可能积累错误；数字和限定条件容易丢失。

存储设计：原文持久化保留；关键事实结构化存储；摘要关联对应原始记录。

查询恢复：当前问题需要细节时检索原文；检查摘要和原文是否冲突；将有价值证据纳入当前预算。

上周一个读者找我复盘字节面试。面试官问了道长对话系统设计题，他觉得挺简单——历史记录存着，窗口装不下就截掉前面的。
	
面试官没否定，只换了个角度：如果用户在第80轮提到第3轮的结论，系统能找回来吗？他说可以用向量库检索。面试官点点头又问：检索出来的历史片段、当前对话、系统提示词，三个加起来超过8K，你打算怎么分？
	
今天就把这套分层记忆架构讲清楚。
	
一、架构权衡
	
8K窗口限制下支撑100轮对话，才是真本事。把大模型当CPU，8K窗口就是内存RAM，100轮历史是硬盘数据。CPU不能直接读硬盘，需要内存中转。核心是聪明地决定什么时候搬什么数据进内存。
	
二、中枢调度
	
上下文协调器像后勤官，要在固定预算内分配8000个Token。不能超预算导致截断错误，也不能留空浪费理解容量。它需要同时向四个记忆层查询：最近原文留多少？摘要选哪份？向量库里有没有相关片段？用户画像里有哪些固定事实？
	
三、分层记忆
	
8000个Token分成四个区域。
	
短期记忆：2500个Token，保留最近三到五轮原文。成本高但价值直接，模型读原文比读摘要准。代价是超出窗口就丢细节。
	
中期摘要：1500个Token，后台模型每隔五轮生成压缩摘要，边对话边压缩，新旧合并形成递归滚动记忆链条。细节会模糊，但逻辑骨架保留。
	
长期外挂：2000个Token，依靠向量数据库和RAG技术。每轮对话都写入数据库，新问题来时做语义检索，动态注入相关片段。把有限窗口变成按需取用的接口。
	
状态管理机：最后500个Token，构建结构化用户画像如姓名、偏好、任务进度、关键事实。始终放在提示词最前面，保证模型在任何轮次都知道用户是谁。没有这层，容出现上下文漂移。
	
四、核心论点
	
面试官真正认可的是三种能力。
	
系统级思维：把CPU、内存、硬盘的三级缓存对应到大模型架构。模型只是计算单元，决定系统上限的是记忆层设计。
	
工程权衡：2500/1500/2000/500这个分配不是理论推导，是反复测试延迟、准确率、成本之后的经验值。能说清每个数字背后的取舍，才是工程成熟度的信号。
	
逻辑锁死：状态表里的内容是显式固定的，摘要会模糊、检索会遗漏，但状态表不会。它保证用户核心身份和任务意图不会被窗口噪声覆盖。
