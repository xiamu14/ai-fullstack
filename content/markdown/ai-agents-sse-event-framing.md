# SSE 比裸流多了什么

ID: sse-event-framing
Library: ai-agents
Version: 2026-10-24.1

模块：系统设计 · 难度：L2

## 题干

Agent 向浏览器推送文本增量和工具进度时，SSE 相比裸 HTTP 字节流提供了什么？

## 参考答案

1. 事件边界：裸字节流的网络分块不能当作完整业务消息；SSE 用规范事件格式界定数据与事件类型。

2. 浏览器接入：可用浏览器 EventSource 处理服务端单向推送；客户端向服务器的指令仍需另行请求或选择双向方案。

3. 协议边界：SSE 是建立在 HTTP 之上的事件流约定；事件帧本身不保证业务任务已经完成或持久化。

AI Agent开发中，目前多是单向通信采用SSE，双向通信采用WebSocket。那么单向通信（服务器到客户端）的通信，为什么用SSE而不是普通的Streamable HTTP呢？

SSE的最大优势在于实现简洁与浏览器原生支持。开发者无须引入任何额外库，即可实现服务端到客户端的单向流式传输，非常适合大语言模型逐字生成输出、长任务进度推送、实时日志流等场景。

SSE（Server-Sent Events）并非独立协议，而是对标准HTTP流式传输（`Transfer-Encoding: chunked`）的标准化语义封装。Agent开发广泛采用SSE，而非裸Streamable HTTP，根本原因在于SSE解决了流式传输中帧同步、断线重连、事件类型分发三大核心痛点，且完美匹配Agent“长下行、短上行”的非对称流量模型。

核心差异（为什么是SSE）：

1. 标准化语义层 vs 裸字节流

普通chunked传输仅提供无边界字节流，服务端推送多个JSON片段时，客户端必须自行处理粘包/半包问题。SSE通过`data:`、`event:`、`id:`字段定义了严格帧格式，浏览器原生`EventSource` API自动按帧解析，且支持通过`event`字段区分“文本增量”“工具调用”“推理日志”等多种事件类型，无需应用层自研分包协议。

2. 内置断线重连机制（高可用关键）

Agent生成长文本（如万字报告）耗时久，网络波动频繁。SSE原生支持`Last-Event-ID`，断线后浏览器自动重连并携带最后收到的ID，服务端可实现断点续推。而普通chunked连接断开即彻底失败，需用户完整重发请求，这在长任务中不可接受。

总结：

SSE在Agent领域的主导地位，源于其协议成熟度（标准化事件边界）、可靠性（自动重连）与工程性价比（低运维、高穿透）的综合优势。裸Streamable HTTP过于简陋（缺语义、无重连），WebSocket又过于沉重（全双工过度设计）。对于任务型Agent，SSE恰处于“够用且最优”的黄金平衡点，是当前流式推送的务实首选。
