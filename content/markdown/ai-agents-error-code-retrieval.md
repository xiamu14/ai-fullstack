## 题干

开发支持 Agent 总把相近的错误码混淆。为什么只做向量检索不够，应该如何改进？

## 参考答案

1. 问题定位：错误码是符号标识而非自然语言语义；相似向量可能对应不同错误码和处理方式。

2. 检索组合：完整明确的错误码优先精确匹配；描述性问题结合关键词与向量召回并融合或重排。

3. 效果验证：构造相近错误码和自然语言描述的测试集；分别检查匹配准确率与检索延迟。

🔥 1. 错误码检索：向量检索为什么会把接口搞挂？
向量模型对符号不敏感，不同错误码向量极近但业务完全不同。我们做向量+BM25 双路召回+RRF 融合+重排；更为高频错误码设计标量直查热路径，跳过大模型，耗时从 0.74s 暴降至 0.010s（加速 78 倍）！

🔥 2. 多 Agent 编排：冷启动 P95 跑 48 秒，怎么留住用户？
单模型串行耗时炸裂。基于 StateGraph 编排 6 个 Agent 并行跑，单个异常局部隔离；配合语义缓存（0.38s 返回，加速 26 倍），冷启动 P95 从 48.58s 降至 6.83s（提速 7 倍），吞吐提升 4 倍！

🔥 3. API Key 泄露防护：怎么保证开发者贴在对话框的凭证不出门？
开发者常把真实凭证贴在报错里。我们设计覆盖 8 类敏感信息的三层脱敏；并将安全审查节点在 LangGraph 末端强收口，从图拓扑上 100% 保证未经脱敏绝不外流！

🔥 4. 多轮会话记忆：第二轮为什么总把上一轮记的信息冲掉？
多轮记忆最大的坑是“空值覆盖”！第二轮抽取的 request_id 本轮为空，若直接覆盖，上一轮凭证全被洗掉！我们在 Redis 实体记忆中做非空增量合并守卫，彻底根除重复追问。
