# 取消任务如何真正停下

ID: task-cancellation
Library: ai-agents
Version: 2026-10-24.1

模块：系统设计 · 难度：L3

## 题干

用户取消 Agent 长任务后，如何停止模型和工具，同时让下一轮会话保持一致？

## 参考答案

1. 信号传播：将取消信号传递到模型请求及正在执行的工具；在步骤边界和等待期间检查取消并停止启动新动作。

2. 进程处置：终止外部命令时考虑子进程或整个进程组；对不能撤回的副作用核对实际状态而非假设已回滚。

3. 历史修复：为未完成的工具调用补充明确的取消结果；下一轮说明中断状态并检查部分执行后再继续。

用户中途取消，Agent 任务怎么停下来？

断开请求，只会停掉你能看到的那部分输出，Agent 已经启动的 Bash 命令可能还在执行，执行到一半的工具可能已经修改了文件，下一轮请求还会因为缺少 tool_result 被 API 直接拒绝。

那么问题来了，取消信号怎么传递下去？

Claude Code 用的是 AbortController，用户按下 Esc，同一个取消信号会传给模型的流式请求，也会传给每一个工具。每个工具拿到的是一个子信号，父信号取消了，子信号跟着取消；

光传递下去还不够，Agent Loop还得主动检查。Claude Code 在流式输出的过程中、每个工具执行之前、重试等待的间隙，都会检查信号有没有被取消，取消了就不再发起新的一步。

那么正在执行的工具怎么停止？
只杀掉 shell 进程是不够的。比如 Agent 执行了 npm run dev，这条命令会启动 Node 子进程，只杀掉父进程，子进程还活着，端口照样被占用。所以要停就整组一起停。

停的信号有两种。SIGTERM 是请求程序退出，程序可以捕获它，先做清理再退出；SIGKILL 是强制结束。Codex比较温和，先给整个进程组发SIGTERM，等50毫秒，再发SIGKILL。Claude Co直接用SIGKILL一次杀掉整棵进程树。

最后，会话历史怎么处理？
A，什么都不做；B，删掉被打断的那一轮回答；C，给每个没有结果的工具调用补一个结果。
我的答案是 B 和 C 组合起来用，A 一定会出问题。

Claude Code 会给被打断的工具补一条结果，告诉模型用户拒绝了这次操作，如果是修改文件，新内容不会写进去，同时停下来等待用户新的指令。
Codex 下一轮还会额外提醒模型“aborted by user”，告诉模型用户是主动打断的，后台进程可能还在运行，模型知道命令可能执行了一半，就会先检查一遍，而不是假装什么都没发生。

最后简单总结下。
取消靠信号层层往下传递，工具要杀掉整个进程组，会话历史要补齐结果；
